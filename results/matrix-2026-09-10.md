## What the better classification changed

The 62KB out of bounds write reached through `DxeCore` was `unknown-crash` before and is
`heap-buffer-overflow (write)` now. It was never unclassifiable -- `asan_print_bug` was
reading the shadow byte for the *start* of the access, which for a long copy that begins
inside its allocation is `0`.

`__ubsan_handle_pointer_overflow` was 1750 identical rows. Each now says whether the base
was null. Every HiiDatabase one is `base 0x0`, which is `ExportPackageList` computing
`(UINT8 *)Buffer + ResultSize` on the size-query pass -- previously established by reading
the source, now stated by the firmware.

## Two new findings, both the harness

`SnpDxe` appears in this matrix and in no earlier one, with two severity 5 reports:

| site | class | size |
|---|---|---|
| `SetMemWrapper.c:63` | heap-buffer-overflow (write) | 8 bytes |
| `ZeroMemWrapper.c:62` | heap-buffer-overflow (write) | 2845 bytes |

Both write into the same allocation, which has 208 usable bytes. The harness calls
`Statistics (This, Reset, StatisticsSize, StatisticsTable)` with the table allocated as
`sizeof (EFI_NETWORK_STATISTICS)` -- 176 bytes -- and `*StatisticsSize` bounded at the
blanket 4096. `Statistics.c:183` then does `ZeroMem (StatisticsTable, *StatisticsSize)`.
The firmware is doing what it was told.

Root cause, in two parts, one fixed:

- **Fixed.** The pointer-to-integer branch of `fuzzable_args` used the blanket 4096 even
  when the size/buffer pair was known, while the by-value branch bounded it by the
  allocation. Both now share `size_limit_for`. `buffer_for_size` also pairs a buffer whose
  name extends the stem (`StatisticsSize` -> `StatisticsTable`), not only one that equals
  it.
- **Not fixed.** For `Statistics` neither helps, because `call-database.json` carries no
  parameter names for that call at all -- only `functions.json`, the declaration, does. With
  no name there is nothing to pair, so the blanket bound is all that applies. This is the
  same shape as the `is_optional` limitation: call-site arguments come through
  `GetAssignmentType` in `CallSiteAnalysis.h`, which never reaches the pass. Fixing it
  means feeding declaration-derived names into the call-site block, which is analysis
  plumbing rather than a generator change.

Until that is done, a severity 5 report against a size the harness chose should be checked
against the harness before it is believed. The generated source is kept beside every
campaign for exactly this.
