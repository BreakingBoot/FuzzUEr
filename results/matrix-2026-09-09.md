## The two that are not NullPointerUse

Everything above except these is either the HiiDatabase pointer-overflow set (nine sites,
confirmed by reading the source: `ExportPackageList` computes `(UINT8 *)Buffer + ResultSize`
on the size-query pass, where its own guard permits `Buffer == NULL`) or a `NullPointerUse`
from the harness handing NULL to a parameter the spec does not mark OPTIONAL.

These two are real sanitizer reports on a `CopyMem`, and want triage:

| protocol | module | class | access | size | hits |
|---|---|---|---|---|---|
| EfiDevicePathUtilities | DevicePathDxe.efi | heap-buffer-overflow | read | 0x5F7D (24445) | 7 |
| EfiFirmwareVolumeBlock | DxeCore.efi | unknown-crash | write | 0xF20F (61967) | 4 |

The shadow around the DevicePath one shows the source starting on a byte with shadow `04`
-- four valid bytes -- inside a run of `FA` redzone, so the copy begins at the edge of an
allocation and runs 24KB past it.

**Not yet confirmed as firmware bugs.** Both are length driven, and the open question is
whether the harness violated a caller contract: `DuplicateDevicePath` and friends walk a
device path using each node's own `Length`, and the UEFI spec expects the caller to supply
a well formed one. That said, the same walk runs on device paths loaded from `Boot####`
variables, which are not under firmware control, so this is worth following rather than
dismissing. Reproduce with `firness.py --reproduce --testcase <file>` against the saved
corpus before drawing a conclusion.
